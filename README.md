# Mobile Integration Hub

Private operational console and secure relay boundary for Android and iOS apps that use AnyFlo as their core data platform.

The console has no application login screen. Protect its administrator UI and `/admin/*` routes using a trusted network or reverse-proxy access control. A public HTTPS domain alone does not protect administration. Mobile runtime and authenticated event-receiver routes must remain reachable by their intended callers. The UI never returns the saved AnyFlo API key.

## What this app does

```text
Android / iOS → Hub → AnyFlo API V2 and Mobile Admission
AnyFlo notification publisher → Hub → FCM / APNs → registered mobile devices
Administrator / Agentic AI → protected Hub console → discovery and API testing
```

AnyFlo remains the workflow manager and source of business data. Hub is a separate, reusable integration service: it keeps the AnyFlo API key on the server, provides API discovery/playground guidance, and handles notification reception and delivery. Each mobile app can implement its own screens and business journey without adding a hardcoded business module to Hub.

The webhook key is **not** the AnyFlo API key, a Google credential, or a mobile access token. It authenticates notification events sent from AnyFlo to Hub. It must never be included in Android/iOS builds.

## Deploy with Easypanel

1. Create a separate project/app service with this repository as its source. Select a reviewed release branch/commit and build the root `Dockerfile`.
2. Mount a **named persistent volume at `/data` before the first deployment**. Use one replica: the current SQLite worker is not designed for multiple processes sharing the database.
3. Set the following environment values (placeholders only):

   ```dotenv
   NODE_ENV=production
   PORT=3000
   DATA_DIR=/data
   HUB_PUBLIC_URL=https://<your-hub-domain>
   ```

4. Route the HTTPS domain to container port `3000`, protect administrator access, and deploy. Verify `GET /health` returns `status: ok`. Health alone does not prove the AnyFlo connection or push delivery.
5. Open the protected Hub UI. Under **AnyFlo connection**, save the AnyFlo app origin, API key label, and token. A fresh volume starts disconnected; no fallback credential is required. The current upstream authentication header is `x-api-key`; the label does not change that header.
6. Click **Test connection**, then **Load workflows** and **Read dictionary**. Confirm this is the intended AnyFlo deployment before testing writes.
7. Configure the shared webhook key as described below, restart/redeploy AnyFlo, and test event reception.
8. Configure `PUSH_APPS_JSON` only when ready for device registration/push. Supply each app's actual FCM/APNs server credentials through protected configuration; see [Push notifications](docs/PUSH_NOTIFICATIONS.md). Restart Hub after environment changes.

Keep the same `/data` volume across updates. It stores the AnyFlo connection, webhook key, device registrations, SQLite delivery queue, and receipts. Protect backups; do not commit or serve this directory. For a full manifest, acceptance checks, rotation, and rollback, see [Deployment Guideline](docs/DEPLOYMENT_GUIDELINE.md).

## How to obtain the webhook key

### Recommended: automatic bootstrap

On the first Hub startup, leave `MOBILE_HUB_WEBHOOK_SECRET` unset. Hub generates **32 cryptographically random bytes**, encoded as 64 hex characters, in:

```text
/data/mobile-hub-webhook-secret
```

The file has permission `0600` and persists across restarts when `/data` is mounted correctly. The key is generated by Hub—not obtained from Google, Firebase, or AnyFlo. The UI deliberately shows only its SHA-256 fingerprint, not its value.

An authorized server operator must retrieve/transfer the file privately through approved server access or a secret manager and set the **exact same text** as `MOBILE_HUB_WEBHOOK_SECRET` on the AnyFlo backend. Do not print it using `cat`, paste it into chat, or include it in logs/screenshots. Use a protected one-time handoff file if the two services are configured by different operators; delete the handoff after verified consumption. Detailed safe generation/install commands are in the [deployment guide](docs/DEPLOYMENT_GUIDELINE.md#safe-generation--handoff).

Configure these on **AnyFlo**, not in the APK:

```dotenv
MOBILE_HUB_ENABLED=true
MOBILE_HUB_URL=https://<your-hub-domain>
# Set MOBILE_HUB_WEBHOOK_SECRET privately to the matching Hub key.
```

`MOBILE_HUB_URL` is the origin only. AnyFlo appends `/internal/events/mobile-notification`. Restart/redeploy the AnyFlo backend after setting its environment.

### Alternative: manually managed key

Generate 32 CSPRNG random bytes using the safe handoff procedure in the deployment guide, and configure the same generated hex text on both services. A nonempty Hub `MOBILE_HUB_WEBHOOK_SECRET` environment variable **overrides the file**. Avoid two competing configuration sources. Never use a memorable password, example value, UUID, API key, or token as the webhook key.

Set `MOBILE_HUB_AUTO_GENERATE_SECRET=false` only if you deliberately want to disable automatic generation. Without an environment key or stored file, reception returns `503`.

### Verify and test

- In **AnyFlo event reception & push diagnostics**, check `webhookConfigured: true` and the active `webhookSecretFingerprint`. Compare SHA-256 fingerprints on both servers without disclosing their keys.
- Use **Test Event → All scenarios → Run Test**. The server supplies its key; the browser never receives it. Expand **Payload and results for Agentic AI** to inspect examples and receipt IDs.
- The UI test uses synthetic events and checks receiver validation/deduplication. It does not change AnyFlo, prove public ingress, or deliver push to a real device.
- To verify the actual connection, send a controlled mention/broadcast from AnyFlo and match its source event ID to an accepted Hub receipt. To verify native push, configure the provider and register a real device; `no_devices` is not successful delivery.

### Rotation

Hub currently accepts **one key at a time**. Coordinate replacement with the AnyFlo operator; do not claim zero-downtime overlap. File-backed replacement takes effect on subsequent requests; environment changes require restart/redeploy. Verify both active fingerprints and a real source event afterward. Follow the [rotation and rollback runbook](docs/DEPLOYMENT_GUIDELINE.md#rotation-and-rollback); never roll back to a compromised key.

## Local development

Use Node.js 22.14 or newer:

```sh
npm ci
npm run check
DATA_DIR=./.data PORT=3000 npm run dev
```

Open `http://localhost:3000`. The `.data/` directory is excluded by `.gitignore`; keep it private and do not expose the development console to an untrusted network. Use a protected persistent volume for deployment.

## Current console capabilities

- service health and whether AnyFlo is configured;
- server-to-server connection to AnyFlo;
- non-secret Mobile Admission readiness report, including the configured redirect URI and whether all server-side prerequisites are present;
- a Mobile Admission token supplied by a developer from an authenticated mobile-app session.
- persistent notification event deduplication, authenticated device registration, FCM/APNs adapters, and sanitized push-delivery diagnostics.

See [Push notifications v1](docs/PUSH_NOTIFICATIONS.md) for environment configuration, device APIs, event contract, staging tests, and delivery limits. The push worker uses a persistent SQLite volume and a single Hub replica.

## Required server environment

Attach persistent storage at `/data`. A new Hub deliberately starts disconnected: the administrator sets the AnyFlo base URL, API key label, and API key in the Hub UI. The key is stored server-side and is never returned by the API or browser UI.

Mobile clients use an AnyFlo Mobile Admission bearer token. The gateway never exposes the server-only API key.

AnyFlo API V2 remains the source of truth for workflow dictionaries, tickets, relations, search, create, and update. Workflow Groups are web-app navigation only; they are not an integration contract. The Hub must not add business modules or per-app workflow configuration.

## Mobile V2 relay

Mobile clients call the supported API V2 surface through `https://<hub>/api/mobile/v1/v2`, with a Mobile Admission bearer token. For example, `GET /api/mobile/v1/v2/workflows/:workflowId/dictionary` and `POST /api/mobile/v1/v2/workflows/:workflowId/tickets/search` relay to their AnyFlo API V2 equivalents. The Hub accepts the documented workflow, ticket, search, create, update, array-row, comment, and history routes only.

Use `$currentUser.id`, `$currentUser.email`, `$currentUser.role.id`, or `$currentUser.department.id` in a query/body filter. The Hub resolves the placeholder from the verified Mobile Admission profile; never put an API key in an APK.

## Agentic AI control plane

For ticket comment mentions, call `GET /api/mobile/v1/v2/tickets/:ticketId/mention-candidates?search=<URL-encoded text>&limit=<count>` with a Mobile Admission Bearer token. Hub forwards the query and upstream response; AnyFlo determines eligible candidates from ticket-workflow tracker access and enforces eligibility when posting comments. Do not invent recipients or fetch a global user list. Use the actual AnyFlo response/comment contract; upstream deployment must include this API V2 endpoint.

The UI provides connection setup, a workflow list, live dictionary/schema inspection, an API V2 playground, a Mobile Admission readiness check, and an agent guide at `GET /agent-guide`. The guide supplies the Hub origin, Mobile Admission contract, readiness result, barebones scope, and explicit App Link/Universal Link next step. The playground is an administrator tool and uses the saved server credential; the mobile runtime must use `/api/mobile/v1/v2` with Mobile Admission instead.

## Mobile Admission readiness

The Hub calls `GET /api/mobile/v1/auth/readiness` on AnyFlo with its saved API key. That AnyFlo route returns only booleans for the Google client ID, Google client secret, Mobile JWT secret, refresh-token storage, plus the non-secret redirect URI. It never returns a credential value and is not a mobile-client endpoint.

A ready report proves that the server-side admission prerequisites are configured. It does not replace live Google consent or App Link / Universal Link verification: the app package or bundle identifier and signing identity must be established first, then the association file must be published on the exact redirect host.
